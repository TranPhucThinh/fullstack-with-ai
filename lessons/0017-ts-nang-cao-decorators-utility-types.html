TypeScript nâng cao — decorators & utility types

Decorators là thứ biến TypeScript thành NestJS — mở hộp đen @Controller()/@Get() để tự viết, cùng utility types giúp viết type linh hoạt như senior.

⏱ ~75 phút · 🎯 Mục tiêu: tự viết được class decorator + method decorator, dùng Partial/Pick/Omit/Readonly, và giải thích được vì sao NestJS cần decorators + experimentalDecorators.

🌉 Bắc cầu từ cái bạn đã biết

Bài 16 bạn có type alias, interface, generics — nền tảng để mô tả dữ liệu. Nhưng mở một file NestJS bất kỳ, thứ đầu tiên đập vào mắt không phải interface, mà là những dấu @: @Controller(), @Get(), @Injectable(), @Body(). Đó là decorators. Bài này mở hộp đen: decorator là gì, tự viết thế nào, và vì sao NestJS chọn nó làm xương sống. Đây là bài cuối cùng chuẩn bị trước khi sang Module 4 (NestJS).

1. Decorator là gì — hàm "bọc" thêm hành vi

Decorator là một hàm TypeScript gọi vào thời điểm khai báo class/method/property/parameter, để thêm hành vi hoặc metadata mà không cần sửa code gốc. Thay vì viết logic log vào từng method, bạn gắn @log lên trên method — decorator tự lo phần còn lại.

💡 Vì sao quan trọng với bạn?

NestJS hoàn toàn xây trên decorators: @Controller() đánh dấu "đây là class nhận request", @Get() đánh dấu "đây là handler cho GET", @Injectable() đánh dấu "class này cho DI quản lý". Hiểu decorator = hiểu vì sao NestJS trông như vậy, thay vì học vẹt cú pháp @.

Decorators chưa phải chuẩn JavaScript chính thức (đang ở stage 3), nên TypeScript cần bật cờ experimentalDecorators. NestJS dùng loại decorator "legacy" này (cùng với emitDecoratorMetadata để phản chiếu type — sẽ bàn khi tới Module 4). Theo TypeScript docs, legacy decorator là một loại khai báo đặc biệt có thể gắn vào class, method, accessor, property hoặc parameter.

tsconfig.json — đã thêm sẵn vào dự án của bạn 
{
  "compilerOptions": {
    "experimentalDecorators": true, // bật decorators (kiểu NestJS)
    ...
  }
}
⚠️ Một "bẫy" thực tế vừa gặp phải (đáng để senior biết)

Dự án có include: ["src"] trong tsconfig — nghĩa là chỉ file trong src/ mới được tsconfig "phủ". tsx tôn trọng include: file nằm ngoài (như thư mục demo/) sẽ không nhận experimentalDecorators → decorator chạy sai (lỗi descriptor.value undefined). Vì vậy demo bài này nằm trong src/, không phải demo/. Đây là minh chứng "hiểu bản chất" đáng giá: cấu hình compile quyết định cách file của bạn được biên dịch, không chỉ nơi bạn đặt nó.

2. Method decorator — bọc lại method

Method decorator nhận 3 tham số: target (prototype), propertyKey (tên method), descriptor (mô tả method — trong đó descriptor.value là hàm gốc). Ta thay descriptor.value bằng hàm mới "bọc" hàm gốc:

Method decorator @log — in args + kết quả mỗi lần gọi (đã verify XANH) 
// Method decorator: nhận (target, propertyKey, descriptor)
function log(target: any, propertyKey: string, descriptor: PropertyDescriptor) {
  const original = descriptor.value            // giữ hàm gốc
  descriptor.value = function (...args: any[]) { // thay bằng hàm bọc
    console.log(`→ ${propertyKey}(${args.join(', ')})`)
    const result = original.apply(this, args)   // gọi hàm gốc
    console.log(`← ${propertyKey} = ${result}`)
    return result
  }
}

class CalcService {
  @log // gắn decorator — không cần sửa thân hàm add
  add(a: number, b: number): number {
    return a + b
  }
}
💡 Cơ chế cốt lõi

Decorator chạy một lần lúc khai báo class (không phải mỗi lần gọi method). Nó "chặn" method gốc, thay bằng hàm bọc — mọi lần gọi sau đều đi qua hàm bọc. Đây là pattern proxy/monkey-patch có kiểm soát: thêm log, đo thời gian, kiểm tra quyền… mà code nghiệp vụ vẫn sạch.

3. Class decorator & decorator factory

Class decorator nhận constructor của class. Muốn truyền thêm tham số (như @Register('CalcService')), ta dùng decorator factory — một hàm trả về decorator:

Class decorator @Register — đăng ký vào "registry" (mô phỏng DI của NestJS) 
// Factory: hàm NHẬN tham số, TRẢ VỀ decorator thật
function Register(name: string) {
  return function (constructor: any) {
    const g = globalThis as any
    g.__registry = g.__registry ?? {}
    g.__registry[name] = constructor   // lưu class vào registry
  }
}

@Register('CalcService') // factory → gọi Register('CalcService') rồi áp decorator
class CalcService { ... }
💡 Đây chính là DI Container của NestJS

@Register('CalcService') đăng ký class vào một "sổ danh bạ" (registry). NestJS làm đúng thế này nhưng lớn hơn: @Injectable() đăng ký class vào DI container, rồi khi cần, container tự tạo instance và inject vào constructor. Bạn vừa tự viết bản thu nhỏ của thứ Module 4 sẽ học — đó là lý do decorators là "nền tảng NestJS".

🧠 Phân biệt: decorator vs factory

@log là decorator trực tiếp (TS gọi ngay log(...)). @Register('CalcService') là factory — vì có dấu ngoặc (), TS gọi Register('CalcService') trước, kết quả trả về mới là decorator. Quy tắc nhớ: có dấu ngoặc = factory. NestJS dùng cả hai: @Injectable() là factory, @Body() là factory… hầu hết đều là factory để nhận tham số cấu hình.

4. NestJS dùng decorators như thế nào

Theo NestJS docs, decorators là cách NestJS "khai báo" mọi thứ mà không cần config tập trung. Bảng ánh xạ:

NestJS decoratorGắn vàoVai trò
@Controller()classĐánh dấu class nhận HTTP request
@Injectable()classĐăng ký vào DI container (như @Register)
@Get()/@Post()methodÁnh xạ method tới route + HTTP verb
@Body()/@Param()parameterBơm dữ liệu request vào tham số

Chưa hết: NestJS bật thêm emitDecoratorMetadata: true + gói reflect-metadata để decorator tự ghi type của tham số constructor — nhờ đó DI biết cần inject đúng loại nào. Đây là phần sẽ đào sâu ở Bài 19-20. Giờ bạn chỉ cần nắm: decorator = cách NestJS gắn metadata vào class/method để framework đọc và điều phối.

5. Utility types — biến đổi type có sẵn

TS có sẵn các utility types giúp "chế" type từ type có sẵn, thay vì viết lại interface mới mỗi lần. Theo TypeScript docs, đây là các type được xây dựng sẵn. Bốn cái bạn dùng nhiều nhất:

src/ts17-decorators-demo.ts — utility types (đã verify XANH) 
interface Course {
  id: number
  title: string
  price: number
  description: string
  published: boolean
}

type NewCourse = Omit<Course, 'id' | 'published'>  // bỏ id + published (server tự sinh)
type CoursePatch = Partial<Course>                  // mọi field thành optional
type CourseCard = Pick<Course, 'id' | 'title'>      // chỉ lấy 2 field
type ReadonlyCourse = Readonly<Course>              // cấm sửa

const draft: NewCourse = { title: 'NestJS', price: 100, description: 'học từ gốc' }
const patch: CoursePatch = { price: 50 }  // chỉ cần sửa 1 field
const card: CourseCard = { id: 1, title: 'NestJS' }
Utility typeLàm gìDùng khi
Partial<T>Mọi field thành optionalCập nhật một phần (PATCH)
Pick<T, K>Chỉ giữ các field KTrả về "bản tóm tắt" (list)
Omit<T, K>Bỏ các field KLoại field server tự sinh (id, mật khẩu)
Readonly<T>Cấm sửa fieldBảo vệ dữ liệu khỏi sửa nhầm
Record<K, V>Ánh xạ key → valueDict/danh sách tra cứu
💡 Vì sao senior thích utility types?

Một interface là nguồn chân lý duy nhất; các biến thể (Omit/Pick/Partial) dẫn xuất từ nó. Khi thêm field vào Course, mọi biến thể tự cập nhật — không sửa 5 chỗ. Ngược lại, viết 5 interface riêng sẽ lệch nhau khi schema đổi. Đây là tư duy "một nguồn, nhiều hình chiếu" — NestJS dùng PartialType()/OmitType() (từ @nestjs/mapped-types) đúng tinh thần này cho DTO.
