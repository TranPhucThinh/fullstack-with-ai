Module 1 · Bài 08

File system, streams, process, env

Hiểu stream là gì, đọc ghi file với fs, và dùng process.env để cấu hình dự án — những mảnh ghép Node nằm ngay dưới framework.

⏱ ~75 phút · 🎯 Mục tiêu: viết được demo đọc/ghi file bằng fs/promises, đọc file qua stream, trả file qua HTTP bằng pipe, và cấu hình server bằng biến môi trường thay vì hardcode.

🌉 Bắc cầu từ cái bạn đã biết

Bài 07 bạn đã thấy for await (const chunk of req) — đọc body request theo từng chunk. Bài này trả lời vì sao dữ liệu tới theo chunk chứ không phải một cục lớn, và mở rộng sang file: Node ⇄ file cũng là một dòng chảy dữ liệu như Node ⇄ HTTP. Bạn sẽ thấy req/res, readFile, createReadStream đều xoay quanh một thứ: stream.

1. Ba cách đọc file trong Node

Trước khi mổ stream, cần biết Node có 3 phong cách API cho mọi thao tác fs (theo tài liệu chính thức Node.js):

Phong cáchĐặc điểmKhi nào dùng
Promises (fs/promises)Trả Promise, dùng await đượcMặc định cho code mới — ví dụ trong bài này
Callback (fs)Nhận callback (err, data) => ...Khi cần hiệu năng tối đa về allocation
Sync (fsSync)Chặn event loop tới khi xongChỉ ở khởi động/script CLI ngắn

Theo docs, readFile đọc toàn bộ nội dung file vào bộ nhớ — nếu không chỉ encoding, dữ liệu trả về là Buffer. Khi dùng { encoding: 'utf8' } thì là string.

💡 Đọc cả file: dễ nhưng phải đúng cỡ

readFile rất tiện cho file cấu hình, JSON nhỏ. Nhưng với file 2GB, nạp cả vào RAM là sai lầm — bài toán của stream bắt đầu từ đây.

2. Đọc/ghi file với fs/promises (demo 1)

Trong thư mục elearning-backend/demo/, tạo file demo-fs-read-write.mjs (thư mục demo/ đã tồn tại từ bài trước):

demo/demo-fs-read-write.mjs 
// Demo 1: fs/promises — đọc CẢ FILE vào bộ nhớ (dễ dùng, nhưng phải xứng cỡ file)
import { readFile, writeFile } from 'node:fs/promises'
import { fileURLToPath } from 'node:url'
import path from 'node:path'

// import.meta.url trỏ tới file đang chạy — từ đó suy ra "cùng thư mục với file này"
const here = fileURLToPath(import.meta.url)
const dataFile = path.join(path.dirname(here), 'data.txt')

const content = await readFile(dataFile, 'utf8')
console.log('Nội dung file:', content)

await writeFile(path.join(path.dirname(here), 'copy.txt'), content.toUpperCase())
console.log('Đã ghi copy.txt (viết hoa)')

Tạo file dữ liệu cùng thư mục:

demo/data.txt 
# File dữ liệu cho demo fs
Hello from data.txt
nodejs 24
Terminal — chạy demo 1 
# Từ thư mục elearning-backend/
node demo/demo-fs-read-write.mjs
✅ Đã kiểm chứng (Node v24.16.0)

Chạy xong in ra nội dung file, tạo copy.txt viết hoa toàn bộ. Kiểu đường dẫn fileURLToPath(import.meta.url) giúp script chạy đúng dù bạn gọi từ thư mục khác.

import.meta.url là URL của chính module đang chạy — file:///...demo/demo-fs-read-write.mjs. fileURLToPath biến nó thành đường dẫn hệ thống, từ đó path.join(dirname(...), 'data.txt') ra file ngay cạnh script. Đây là cách đúng để định vị file tương đối với code, thay vì phụ thuộc thư mục bạn đang đứng khi gõ lệnh.

⚠️ Cẩn thận khi gọi lệnh

readFile('./data.txt') tương đối với thư mục bạn đang đứng trong terminal (cwd), không phải vị trí file script. Chạy từ elearning-backend/ mà viết 'data.txt' thẳng sẽ báo ENOENT. Lưu ý này đúng với mọi API fs nhận đường dẫn.

3. Stream là gì — vì sao dữ liệu tới theo chunk

Theo tài liệu chính thức, Node có 4 loại stream:

LoạiBản chấtVí dụ
ReadableNguồn dữ liệu — đọc rafs.createReadStream, req, process.stdin
WritableĐích dữ liệu — ghi vàofs.createWriteStream, res, process.stdout
DuplexVừa đọc vừa ghinet.Socket (TCP)
TransformDuplex có biến đổi dữ liệuzlib.createGzip

Key insight: req và res bạn dùng ở bài 06-07 chính là stream. Docs viết rõ: "req là http.IncomingMessage — một readable stream; res là http.ServerResponse — một writable stream". Stream là cách Node truyền dữ liệu từng phần (chunk) thay vì chờ đủ cả khối — giống vòi nước chứ không phải thùng nước.

💡 Vì sao chunk?

Dữ liệu (file, mạng, socket) không tới một lúc. Server đọc file 2GB từ đĩa: nếu chờ đủ 2GB mới xử lý, bạn tốn 2GB RAM và client chờ rất lâu. Stream cho phép xử lý và trả về ngay khi có phần đầu tiên — giảm bộ nhớ, giảm độ trễ, và nối được nguồn chậm với đích nhanh.

Kích thước mỗi chunk do highWaterMark quyết định: mức "ngưỡng" bộ đệm trước khi stream tạm dừng xin thêm dữ liệu. Với fs.createReadStream, mặc định là 64 * 1024 bytes (= 64KB). Đây không phải giới hạn cứng — là threshold, không phải limit, theo docs.

4. Đọc file theo stream (demo 2 — thấy chunk bằng mắt)

Tạo file giả 2MB trong demo/ rồi viết demo đọc:

Terminal — tạo file giả 2MB 
# Từ elearning-backend/ — tạo file giả 2MB (dùng cho demo stream)
dd if=/dev/urandom of=demo/SW.js bs=1024 count=2048
demo/demo-stream-chunks.mjs 
// Demo 2: stream Readable — đọc theo CHUNK (phù hợp file lớn, không cần nạp hết vào RAM)
import { createReadStream } from 'node:fs'

// highWaterMark: 64KB mặc định (bài học: cỡ chunk do mình chọn)
const stream = createReadStream('SW.js', { highWaterMark: 64 * 1024 })

let chunkIndex = 0
let totalBytes = 0

// 'data' event: mỗi lần có chunk sẵn sàng thì callback chạy
stream.on('data', (chunk) => {
  chunkIndex++
  totalBytes += chunk.length
  console.log(`chunk ${chunkIndex}: ${chunk.length} bytes`)
})

// 'end' event: đã đọc xong toàn bộ file
stream.on('end', () => {
  console.log(`Xong! Tổng ${totalBytes} bytes qua ${chunkIndex} chunks`)
})
Terminal — chạy demo 2 
node demo/demo-stream-chunks.mjs
✅ Kết quả đã kiểm chứng (Node v24.16.0)

Trong thư mục demo/, chạy node demo-stream-chunks.mjs: 2MB đọc thành 32 chunk × 65536 bytes, tổng 2097152 bytes. Nếu tăng highWaterMark lên 1MB, số chunk giảm còn 2 — chunk to hơn thì tốn RAM hơn nhưng ít lần đọc hơn. Đây là đánh đổi bạn sẽ gặp khi tinh chỉnh.

5. Trả file qua HTTP bằng pipe (demo 3 — chạm tới dự án thật)

Demo 2 mới chỉ đọc. Giờ nối stream đọc file với stream ghi HTTP: readStream.pipe(res). Dữ liệu chảy từ file vào response, không nạp cả file vào RAM.

demo/demo-http-stream.mjs 
// Demo 3: HTTP server + stream — không nạp hết file vào RAM, vừa đọc vừa trả
import { createServer } from 'node:http'
import { createReadStream } from 'node:fs'
import { stat } from 'node:fs/promises'
import { join, dirname } from 'node:path'
import { fileURLToPath } from 'node:url'

const here = dirname(fileURLToPath(import.meta.url)) // thư mục chứa file này
const server = createServer(async (req, res) => {
  // Chỉ phục vụ đúng route /download
  if (req.method !== 'GET' || req.url !== '/download') {
    res.writeHead(404, { 'Content-Type': 'text/plain; charset=utf-8' })
    res.end('Không tìm thấy')
    return
  }

  const filePath = join(here, 'SW.js') // chính file giả 2MB trong demo
  const { size } = await stat(filePath) // lấy kích thước file

  // Gửi header Content-Length TRƯỚC — client biết chính xác độ dài tải về
  res.writeHead(200, {
    'Content-Type': 'text/javascript; charset=utf-8',
    'Content-Length': size,
  })

  // Nối stream đọc file với response — dữ liệu chảy dần, không giữ 2MB trong RAM
  const readStream = createReadStream(filePath)
  readStream.pipe(res)
})

const PORT = 4012
server.listen(PORT, () => console.log(`Server stream: http://localhost:${PORT}/download`))
Terminal — chạy demo 3 & kiểm tra 
node demo/demo-http-stream.mjs
Terminal 2 — curl 
curl -s -o /dev/null -D - http://localhost:4012/download
# HTTP/1.1 200 OK
# Content-Length: 2097152
# ...

# Lưu file tải về và so kích thước với bản gốc
curl -s http://localhost:4012/download -o /tmp/downloaded-SW.js
ls -l /tmp/downloaded-SW.js demo/SW.js
💡 Vì sao phải set Content-Length?

Nếu không set, client không biết khi nào file hết — với connection keep-alive, client sẽ chờ tới timeout. pipe tự gọi end() khi stream đọc xong, nhưng header phải có từ trước. Node có thể trả theo Transfer-Encoding: chunked nếu bạn không set Content-Length — đúng hơn cho stream, nhưng với file có kích thước biết trước thì Content-Length chuẩn hơn.

⚠️ Demo 3 là code học — chưa phải production

Trong demo, đường dẫn file nằm cứng trong code và không hạn chế loại file — ai gọi /download cũng lấy được SW.js. Khi làm thật sẽ đọc path.join(here, ...) từ env, kiểm tra .. để chống path traversal. Đó là nội dung bài bảo mật sau này.

6. process & env — cấu hình không hardcode

Theo tài liệu process, mỗi tiến trình Node có sẵn:

Thuộc tínhÝ nghĩaVí dụ
process.argvMảng tham số dòng lệnh — phần tử 0 là đường dẫn node, 1 là file script, còn lại là tham sốnode a.mjs x y → ['/usr/local/bin/node', '/path/a.mjs', 'x', 'y']
process.cwd()Thư mục hiện tại khi khởi động tiến trình/Users/you/project
process.envObject chứa biến môi trường của tiến trình{ NODE_ENV: 'production', ... }
process.exitCodeMã thoát để shell biết thành công (0) hay lỗi (≠0)đặt 1 khi thiếu config

Trong demo 4, ta in ra 4 thứ đó, rồi chạy lại với biến môi trường:

demo/demo-process-env.mjs 
// Demo 4: process + env — argv, cwd, env, exit code
console.log('argv =', process.argv)
console.log('cwd  =', process.cwd())
console.log('NODE_ENV =', process.env.NODE_ENV ?? '(chưa đặt)')
console.log('SELF_PORT =', process.env.SELF_PORT ?? '(chưa đặt)')
Terminal — chạy demo 4 
# Từ elearning-backend/
node demo/demo-process-env.mjs one two=three

# Đặt biến môi trường ngay trước lệnh — chỉ tồn tại trong lần chạy này
NODE_ENV=production SELF_PORT=4012 node demo/demo-process-env.mjs
✅ Đã kiểm chứng (Node v24.16.0)

Lần đầu: argv gồm đường dẫn node, file script, rồi 'one', 'two=three'; NODE_ENV trả về (chưa đặt). Lần hai: NODE_ENV=production, SELF_PORT=4012 xuất hiện trong process.env.

💡 Vì sao dùng env?

Cổng, URL database, secret... khác nhau giữa máy local và production. Hardcode trong code khiến bạn phải sửa file khi triển khai — và rò rỉ secret vào git. process.env cho phép cùng một code, nhiều môi trường: shell quyết định, code chỉ đọc. Đây là lý do mọi framework (Express đọc process.env.PORT, NestJS dùng ConfigModule) đều dựa trên env.

7. exit code — cho shell biết lệnh thành công hay thất bại

Khi server cấu hình thiếu, ta không muốn chạy tiếp với giá trị sai. Demo 5 đặt process.exitCode = 1:

demo/demo-exit-code.mjs 
// Demo 5: exit code — process.exitCode để shell biết lệnh thành công hay thất bại
import process from 'node:process'

const required = process.env.REQUIRED_FLAG // biến tùy chọn cần có

if (!required) {
  console.error('Thiếu REQUIRED_FLAG — không chạy được')
  process.exitCode = 1 // KHÔNG gọi process.exit() — để stdout/stderr được flush
} else {
  console.log(`Nhận được flag: ${required}`)
}
Terminal — chạy demo 5 
# Thiếu biến — lệnh "thất bại", shell thấy exit code 1
node demo/demo-exit-code.mjs
echo $?

# Đủ biến — thành công, exit 0
REQUIRED_FLAG=abc node demo/demo-exit-code.mjs
echo $?
⚠️ Không lạm dụng process.exit()

Docs cảnh báo: gọi process.exit() ép tiến trình thoát ngay, có thể cắt mất dữ liệu stdout đang được ghi bất đồng bộ. Thay vì thế, đặt process.exitCode rồi để tiến trình thoát tự nhiên khi không còn việc gì trong event loop.

8. Bắt lỗi file không tồn tại (demo 6 — chống crash)

Đọc file vắng mặt sẽ reject với ENOENT. Nếu không bắt, tiến trình không tải được. Hãy luôn try/catch quanh fs ở code bất đồng bộ:

demo/demo-error.mjs 
// Demo 6: bắt lỗi ENOENT — đọc file không tồn tại nhưng KHÔNG crash
import { readFile } from 'node:fs/promises'

try {
  await readFile('./khong-ton-tai.txt', 'utf8')
} catch (err) {
  console.log('Bắt được lỗi, code:', err.code)
  console.log('Thông điệp:', err.message)
}
console.log('Chương trình vẫn chạy tiếp tới dòng này ✅')
Terminal — chạy demo 6 
node demo/demo-error.mjs
✅ Đã kiểm chứng (Node v24.16.0)

In ra code: ENOENT, message: ENOENT: no such file...', rồi dòng tiếp tục chạy bình thường, exit 0. Không crash.

9. Ghép lại dự án: cấu hình PORT bằng env

Giờ apply vào dự án thật: thay const PORT = 4000 cứng trong src/server.ts bằng env (code hiện có của bạn cũng được — ý tưởng là đọc từ process.env):

src/server.ts — phần cuối (chỉ sửa 2 dòng) 
// PORT đọc từ env: chạy "PORT=5000 npm run dev" sẽ lắng nghe 5000, mặc định 4000
const PORT = Number(process.env.PORT ?? 4000)
const HOST = '0.0.0.0'

server.listen(PORT, HOST, () => {
  console.log(`✅ Server running at http://localhost:${PORT}`)
})
Terminal — kiểm tra 
# Vẫn chạy mặc định 4000
npm run dev

# Hoặc ép cổng khác — cùng code, cổng khác
PORT=5000 npm run dev
curl -s http://localhost:5000/api/courses | head -c 120
echo ''
✅ Bạn vừa đạt được
  • Đọc/ghi file bằng fs/promises (readFile/writeFile) với đường dẫn bền vững qua import.meta.url
  • Hiểu stream: Readable/Writable, highWaterMark, dữ liệu chảy theo chunk
  • Trả file qua HTTP bằng readStream.pipe(res) + Content-Length — không nạp cả file vào RAM
  • Dùng process.argv/cwd()/env/exitCode, và cấu hình PORT bằng env thay vì hardcode

10. Câu hỏi tư duy (bắc cầu sang bài sau)

Bạn đã thấy stream xử lý dữ liệu tuần tự từng chunk. Nhưng khi request tới, server phải chạy nhiều bước giữa chừng: ghi log, kiểm tra auth, đọc body, rồi mới tới handler route. Làm sao tổ chức những bước dùng chung này cho mọi route mà không lặp code? Đó chính là middleware — khái niệm lõi của Express, và bài 09 nói về vì sao framework sinh ra để giải bài toán này.
