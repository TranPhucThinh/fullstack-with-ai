Auth cơ bản bằng Express — bcrypt, JWT

Đăng ký/đăng nhập với mật khẩu hash (bcrypt) và token (JWT) — xương sống bảo mật của mọi hệ thống.

⏱ ~90 phút · 🎯 Mục tiêu: hiểu vì sao phải hash mật khẩu, tạo register/login, bắt lỗi email trùng (409), và bảo vệ route bằng JWT middleware.

🌉 Bắc cầu từ cái bạn đã biết

Bài 12 bạn đã có CRUD users với PostgreSQL. Bài 13 bạn đã thiết kế database quan hệ. Nhưng hệ thống thật cần xác thực: ai được phép tạo khóa, ai mua khóa. Bài này giải bài toán: lưu mật khẩu an toàn thế nào (bcrypt) và chứng minh "tôi là ai" sau khi đăng nhập (JWT).

1. Vì sao KHÔNG được lưu mật khẩu dạng thô?

Nếu lưu mật khẩu dạng text trong database, một khi database bị rò rỉ (data breach), kẻ tấn công đọc được toàn bộ mật khẩu người dùng. Người dùng thường dùng lại mật khẩu ở nhiều nơi → hậu quả lan rộng.

💡 Giải pháp: hash mật khẩu

Hash là hàm một chiều: từ mật khẩu ra chuỗi hash dễ, nhưng từ hash không thể suy ngược ra mật khẩu. Khi đăng nhập, ta hash mật khẩu nhập vào rồi so sánh với hash đã lưu. Kẻ đánh cắp database chỉ có hash — vô dụng nếu hash đủ mạnh.

Theo OWASP Password Storage Cheat Sheet, mật khẩu phải được hash bằng thuật toán chậm, có salt (vd bcrypt, scrypt, argon2) — KHÔNG dùng MD5/SHA1 (quá nhanh, dễ brute-force). bcrypt là lựa chọn phổ biến nhất trong Node.

2. bcrypt & JWT — xương sống auth

Terminal — bcrypt hash & compare (đã verify XANH) 
# bcrypt@6.0.0, jsonwebtoken@9.0.3 đã cài trong dự án
node -e "import('bcrypt').then(async b => {
  const hash = await b.hash('secret123', 10)
  console.log('hash:', hash)
  console.log('compare dung:', await b.compare('secret123', hash))
  console.log('compare sai:', await b.compare('sai', hash))
})"

Kết quả: hash là chuỗi dài (vd $2b$10$...), compare trả true với đúng mật khẩu, false với sai. Số 10 là cost factor — càng cao càng chậm (khó brute-force) nhưng tốn CPU.

JWT (JSON Web Token) theo jwt.io gồm 3 phần: header.payload.signature. Phần signature ký bằng secret — server verify được token có bị sửa.

Terminal — JWT sign & verify (đã verify XANH) 
node -e "import('jsonwebtoken').then(jwt => {
  const token = jwt.sign({ userId: 1 }, 'secret-demo', { expiresIn: '1h' })
  console.log('token:', token)
  console.log('verify:', jwt.verify(token, 'secret-demo'))
  try { jwt.verify(token, 'sai-secret') } catch (e) { console.log('sai secret:', e.message) }
})"
💡 Vì sao JWT quan trọng?

JWT cho phép server không cần lưu session (stateless): chỉ verify chữ ký bằng secret là biết token hợp lệ và payload chứa userId. Đây là nền cho mọi auth hiện đại, và NestJS sau này cũng dùng JWT.

4. Viết auth vào server.ts

Thêm import bcrypt + jwt ở đầu src/server.ts:

src/server.ts — thêm import 
import bcrypt from 'bcrypt'
import jwt from 'jsonwebtoken'

const JWT_SECRET = 'secret-dev-doi-sau' // ⚠️ bài sau học giấu vào .env
src/server.ts — register (hash + bắt 409) 
// Đăng ký: hash mật khẩu rồi lưu, trả token
app.post('/api/auth/register', async (req, res) => {
  const { email, name, password } = req.body ?? {}
  if (!email || !name || !password) {
    res.status(400).json({ error: 'email, name, password là bắt buộc' })
    return
  }
  const hash = await bcrypt.hash(password, 10)
  try {
    const { rows } = await pool.query(
      'INSERT INTO users (email, name, password_hash) VALUES ($1,$2,$3) RETURNING id, email, name',
      [email, name, hash],
    )
    const token = jwt.sign({ userId: rows[0].id }, JWT_SECRET, { expiresIn: '1h' })
    res.status(201).json({ user: rows[0], token })
  } catch (e) {
    if (e.code === '23505') {
      res.status(409).json({ error: 'Email đã tồn tại' })
      return
    }
    throw e
  }
})
⚠️ Bắt lỗi 23505 — yếu điểm bài 12

Bài 12 ghi nhận email trùng → 500. Giờ bắt mã lỗi PostgreSQL 23505 (UNIQUE) và trả 409 Conflict — đúng chuẩn REST.

src/server.ts — login (compare + trả token) 
// Đăng nhập: tìm user theo email, so hash, trả token
app.post('/api/auth/login', async (req, res) => {
  const { email, password } = req.body ?? {}
  const { rows } = await pool.query('SELECT * FROM users WHERE email=$1', [email])
  if (rows.length === 0 || !(await bcrypt.compare(password, rows[0].password_hash))) {
    res.status(401).json({ error: 'Sai email hoặc mật khẩu' })
    return
  }
  const token = jwt.sign({ userId: rows[0].id }, JWT_SECRET, { expiresIn: '1h' })
  res.json({ token })
})
💡 Vì sao trả 401 chung "Sai email hoặc mật khẩu"?

Nếu trả "Email không tồn tại" riêng, kẻ tấn công dò được email nào đã đăng ký (user enumeration). Trả chung một thông điệp mơ hồ là chuẩn bảo mật OWASP.

src/server.ts — middleware auth + route /api/me 
// Middleware auth: đọc token, verify, gắn userId vào req
function auth(req, res, next) {
  const header = req.headers.authorization
  if (!header?.startsWith('Bearer ')) {
    res.status(401).json({ error: 'Thiếu token' })
    return
  }
  try {
    const decoded = jwt.verify(header.slice(7), JWT_SECRET)
    req.userId = decoded.userId // gắn userId cho handler dùng
    next()
  } catch {
    res.status(401).json({ error: 'Token không hợp lệ hoặc hết hạn' })
  }
}

// Route được bảo vệ: chỉ chạy khi token hợp lệ
app.get('/api/me', auth, async (req, res) => {
  const { rows } = await pool.query('SELECT id, email, name FROM users WHERE id=$1', [req.userId])
  res.json(rows[0])
})
💡 Middleware auth — tái sử dụng

Middleware auth là hàm (req, res, next) — đúng pattern bài 11. Đặt trước bất kỳ route cần bảo vệ (vd sau này app.post('/api/courses', auth, ...)). Đây là tiền đề của guards trong NestJS.
