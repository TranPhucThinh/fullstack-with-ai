Thiết kế database e-learning — cấp PRO (chuẩn hóa, khóa ngoại nâng cao, index)

Nâng cấp ERD e-learning từ "3 bảng đúng" lên "schema production": chuẩn hóa 1NF/2NF/3NF, ON DELETE/CASCADE, index & EXPLAIN, JOIN + thống kê, timestamps, migration.

⏱ ~120 phút · 🎯 Mục tiêu: thiết kế schema e-learning đủ cho production — hiểu chuẩn hóa, chọn đúng ON DELETE, đặt index đúng chỗ, thống kê bằng GROUP BY/HAVING, và nghĩ tới migration/versioning.

🌉 Bắc cầu từ cái bạn đã biết

Bài 13 bạn đã có users → enrollments → courses chạy được, với khóa ngoại (REFERENCES), CHECK, UNIQUE tổ hợp và JOIN 3 bảng. Giờ bạn nhìn lại schema đó bằng mắt senior: dữ liệu lớn thì chậm ở đâu? Xóa khóa học thì enrollment ra sao? Thêm "bài giảng" (lessons) và "danh mục" (categories) thì chuẩn hóa thế nào? Đây là phần phân biệt "thiết kế cho chạy" với "thiết kế cho production".

2. Chuẩn hóa dữ liệu — 1NF, 2NF, 3NF

Bài 13 nói "tách bảng" một cách trực giác. Giờ ta đặt tên chính xác cho nó: chuẩn hóa (normalization) là quá trình bỏ trùng lặp theo từng bậc. Ba bậc đầu đủ cho hầu hết hệ thống:

BậcQuy tắcVi phạm (ví dụ)Cách sửa
1NFMỗi ô chỉ chứa 1 giá trị nguyên tử (không mảng, không chuỗi ngăn cách)cột tags = "nestjs,sql,design"Tách bảng tags + bảng nối
2NFKhông phụ thuộc hàm riêng phần vào 1 phần của khóa tổ hợpBảng có khóa (user_id, course_id) mà course_title chỉ phụ thuộc course_idĐưa course_title về bảng courses
3NFKhông phụ thuộc bắc cầu (cột không khóa phụ thuộc qua cột không khóa khác)trong enrollments lưu course_title (qua course_id)Chỉ lưu course_id, title nằm ở courses
Ví dụ vi phạm 1NF → chuẩn hóa 
-- SAI (1NF): một cột chứa nhiều giá trị, không thể lọc "khóa có tag sql" bằng SQL sạch
CREATE TABLE courses (id SERIAL PRIMARY KEY, tags TEXT);  -- tags = 'nestjs,sql'

-- ĐÚNG: tách bảng tags + bảng nối course_tags (nhiều-nhiều)
CREATE TABLE tags (id SERIAL PRIMARY KEY, name TEXT UNIQUE NOT NULL);
CREATE TABLE course_tags (
  course_id INTEGER NOT NULL REFERENCES courses(id),
  tag_id    INTEGER NOT NULL REFERENCES tags(id),
  PRIMARY KEY (course_id, tag_id)
);
💡 Vì sao chuẩn hóa quan trọng với senior?

Chuẩn hóa không phải lý thuyết suông — nó quyết định bạn có truy vấn được dữ liệu một cách tổng quát hay không. Vi phạm 1NF (nhét mảng vào 1 cột) thì "đếm khóa theo tag", "lọc khóa theo tag" thành cơn ác mộng. Đôi khi ta cố ý phá chuẩn (denormalize) vì hiệu năng — nhưng phải biết mình đang phá và đánh đổi gì. Đó là tư duy senior, không phải "chuẩn hóa bằng mọi giá".

3. Schema e-learning mở rộng — đủ cho production

ERD đầy đủ hơn cho e-learning — thêm categories (danh mục), lessons (bài giảng), và liên kết instructor (giảng viên) trỏ tới chính bảng users:

🗺️ ERD mở rộng — users đóng 2 vai trò (học viên & giảng viên)
categories 1 ── * courses 1 ── * lessons
                 │  1
                 │  * enrollments * ── 1 users
                 │
                 └── instructor_id ──> users (SET NULL)
BảngVai tròCột chính
categoriesDanh mục khóa (Backend, Database…)id, name, slug UNIQUE
coursesKhóa họcid, title, price, description, category_id, instructor_id, created_at…
lessonsBài giảng thuộc 1 khóa (1-nhiều)id, course_id FK, title, position, duration
enrollmentsHọc viên đăng ký khóa (nhiều-nhiều)user_id FK, course_id FK, enrolled_at

Điểm tinh tế: users đóng hai vai trò. Một user có thể là học viên (qua enrollments) và là giảng viên (qua courses.instructor_id). Ta không tạo bảng instructors riêng — chỉ trỏ khóa ngoại về users. Khi nào quyết định tách bảng mới? Khi instructor có thuộc tính riêng (bio, rating, số khóa…). Chưa cần thì chưa tách.

Terminal — thêm categories + lessons, mở rộng courses 
docker exec -it elearning-postgres psql -U elearning -d elearning -c "CREATE TABLE categories (
  id SERIAL PRIMARY KEY,
  name TEXT NOT NULL,
  slug TEXT NOT NULL UNIQUE
);"

docker exec -it elearning-postgres psql -U elearning -d elearning -c "CREATE TABLE lessons (
  id SERIAL PRIMARY KEY,
  course_id INTEGER NOT NULL REFERENCES courses(id) ON DELETE CASCADE,
  title TEXT NOT NULL,
  content TEXT,
  position INTEGER NOT NULL DEFAULT 0,
  duration_minutes INTEGER
);"

docker exec -it elearning-postgres psql -U elearning -d elearning -c "ALTER TABLE courses
  ADD COLUMN category_id INTEGER REFERENCES categories(id),
  ADD COLUMN instructor_id INTEGER REFERENCES users(id) ON DELETE SET NULL;"
⚠️ Đọc kỹ hai lựa chọn ở đây

lessons.course_id ... ON DELETE CASCADE — xóa khóa thì xóa luôn bài giảng (bài giảng không thể tồn tại nếu không có khóa). Nhưng courses.instructor_id ... ON DELETE SET NULL — xóa giảng viên thì giữ khóa, chỉ bỏ tham chiếu về NULL. Vì sao khác nhau? Mục tiếp theo.

4. ON DELETE / ON UPDATE — kiểm soát toàn vẹn khi xóa

Theo PostgreSQL docs, khóa ngoại có thể khai báo hành động khi dòng cha bị DELETE/UPDATE. Ba lựa chọn chính:

Hành độngKhi xóa dòng chaDùng khi
RESTRICT (mặc định)Chặn xóa — báo lỗi nếu còn dòng con tham chiếuKhông muốn mất dữ liệu "ngoài ý muốn"
CASCADEXóa luôn các dòng conDòng con không có ý nghĩa nếu cha mất (lessons của course)
SET NULLGiữ dòng con, bỏ khóa ngoại về NULLDòng con vẫn có giá trị dù cha mất (course khi instructor bị xóa)
Terminal — thử 3 hành vi (sau khi đã ALTER ở mục 3) 
# 1) RESTRICT (mặc định): course 1 còn enrollment -> database CHẶN xóa
docker exec -it elearning-postgres psql -U elearning -d elearning -c "DELETE FROM courses WHERE id = 1;"
# ERROR: update or delete on table "courses" violates foreign key constraint ... on table "enrollments"

# 2) CASCADE: thêm 1 lesson cho course 2, rồi xóa course 2 -> lesson bay theo
docker exec -it elearning-postgres psql -U elearning -d elearning -c "INSERT INTO lessons (course_id, title, position) VALUES (2, 'Mở đầu', 1);"
docker exec -it elearning-postgres psql -U elearning -d elearning -c "DELETE FROM courses WHERE id = 2;"
# DELETE 1 — và lesson của course 2 cũng bị xóa (CASCADE)
💡 Vì sao chọn đúng ON DELETE là kỹ năng senior?

Chọn sai nghĩa là hoặc mất dữ liệu (CASCADE quá tay) hoặc kẹt dữ liệu (RESTRICT quá chặt, không xóa được gì vì mắc ràng buộc). Quy tắc ghi nhớ: "dòng con sống được thiếu cha không?" — sống được → SET NULL hoặc RESTRICT; không sống được → CASCADE. Với tiền bạc (orders, payments) thì hầu như luôn RESTRICT: bạn không bao giờ muốn xóa user kéo theo xóa lịch sử thanh toán.

5. Index — vì sao, khi nào, và kiểm tra bằng EXPLAIN

Bài 13 chưa nói tới: khóa chính tự có index, nhưng cột khóa ngoại thì KHÔNG. Khi enrollments có hàng triệu dòng, truy vấn "khóa học của user 1" sẽ quét toàn bảng — chậm dần theo cấp số nhân. Index giúp PostgreSQL nhảy thẳng tới đúng dòng.

Terminal — thấy Seq Scan rồi biến thành Index Scan 
# 1) Xem kế hoạch truy vấn — chưa có index trên user_id
docker exec -it elearning-postgres psql -U elearning -d elearning -c "EXPLAIN ANALYZE SELECT * FROM enrollments WHERE user_id = 1;"
# Seq Scan on enrollments (cost=...) — đọc TUẦN TỰ cả bảng

# 2) Tạo index cho cột khóa ngoại
docker exec -it elearning-postgres psql -U elearning -d elearning -c "CREATE INDEX idx_enrollments_user_id ON enrollments(user_id);"

# 3) Chạy lại EXPLAIN -> Index Scan — chỉ đọc vài dòng khớp
docker exec -it elearning-postgres psql -U elearning -d elearning -c "EXPLAIN ANALYZE SELECT * FROM enrollments WHERE user_id = 1;"
Khi nào tạo indexKhi nào chưa cần
Cột khóa ngoại (JOIN / lọc thường xuyên)Bảng nhỏ, vài trăm dòng (Seq Scan nhanh hơn)
Cột trong WHERE/ORDER BY thường xuyênCột ít được lọc, bảng bị ghi nhiều (mỗi index làm INSERT chậm thêm)
Cột có UNIQUE constraint (PG tự tạo index)Đoán mò — index không miễn phí: tốn dung lượng + chậm ghi
🧠 Mẹo senior

Đừng đánh index tràn lan từ đầu. Hãy để EXPLAIN ANALYZE lên tiếng trước: thấy Seq Scan trên bảng lớn trong câu truy vấn hay gọi → mới thêm index. Index là đánh đổi giữa đọc nhanh và ghi chậm — đúng tinh thần "ra quyết định có lý do" của senior.

6. JOIN nâng cao — LEFT JOIN + GROUP BY/HAVING

Bài 13 JOIN để trả lời "user học khóa nào". Senior còn trả lời câu hỏi thống kê: "khóa nào đông học viên nhất", "khóa nào chưa ai học". Cần LEFT JOIN + GROUP BY + HAVING:

Terminal — đếm học viên từng khóa (kể cả khóa 0 người) 
docker exec -it elearning-postgres psql -U elearning -d elearning -c "SELECT c.title, COUNT(e.user_id) AS so_hoc_vien
FROM courses c
LEFT JOIN enrollments e ON e.course_id = c.id
GROUP BY c.id, c.title
ORDER BY so_hoc_vien DESC;"

Vì sao LEFT JOIN chứ không phải JOIN (INNER)? Vì JOIN chỉ giữ khóa có enrollment — khóa chưa ai đăng ký bị biến mất khỏi kết quả. LEFT JOIN giữ toàn bộ courses bên trái, khóa nào không có enrollment thì COUNT trả 0.

Terminal — khóa nào CHƯA có học viên (HAVING) 
docker exec -it elearning-postgres psql -U elearning -d elearning -c "SELECT c.title, COUNT(e.user_id) AS so_hoc_vien
FROM courses c
LEFT JOIN enrollments e ON e.course_id = c.id
GROUP BY c.id, c.title
HAVING COUNT(e.user_id) = 0;"
💡 WHERE vs HAVING — lỗi phổ biến của junior

WHERE lọc từng dòng trước khi gộp; HAVING lọc kết quả sau khi GROUP BY. Bạn không thể viết WHERE COUNT(...) = 0 — vì lúc WHERE chạy thì COUNT chưa tồn tại. Đây là câu hỏi phỏng vấn kinh điển.

7. Timestamps, soft delete & khóa thay thế

Ba thói quen giúp schema "production-ready":

Terminal — thêm cột quản trị 
docker exec -it elearning-postgres psql -U elearning -d elearning -c "ALTER TABLE courses
  ADD COLUMN created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  ADD COLUMN updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  ADD COLUMN deleted_at TIMESTAMPTZ;"
  • created_at / updated_at — biết khi nào tạo/sửa; updated_at thường phải cập nhật bằng trigger hoặc code (bài sau bàn TypeORM tự làm).
  • Soft delete (deleted_at) — thay vì DELETE vĩnh viễn, đánh dấu thời điểm xóa. Truy vấn chỉ lọc WHERE deleted_at IS NULL. Lợi: khôi phục được, giữ lịch sử. Đây là lý do người ta chọn SET NULL/RESTRICT thay vì CASCADE cho dữ liệu quan trọng.
  • Khóa thay thế (surrogate key) — SERIAL id là khóa thay thế, không mang ý nghĩa nghiệp vụ. Đối lập với khóa tự nhiên (vd email làm khóa). Quy tắc: khóa chính nên là surrogate (ổn định, không bao giờ đổi), khóa tự nhiên đặt UNIQUE riêng (vd email) — đúng như users của bạn.
⚠️ Soft delete có cái giá của nó

Mọi câu truy vấn từ nay phải nhớ thêm deleted_at IS NULL, và unique constraint (email) sẽ xung đột khi tạo lại bản ghi cùng email đã xóa. Đừng áp dụng soft delete vô tội vạ — chỉ dùng cho dữ liệu cần khôi phục hoặc giữ lịch sử (users, courses, orders), không dùng cho bảng trung gian như enrollments.

8. Migration & seed — schema phải tái lập được

Cho tới giờ bạn chạy lệnh CREATE TABLE tay. Vấn đề: đồng nghiệp clone code về, hay deploy máy mới — làm sao tái lập đúng schema? Câu trả lời là migration: mỗi thay đổi schema là một file được version, chạy theo thứ tự. Seed là file dữ liệu mẫu ban đầu.

Tư duy migration (chưa cần tool — bài 23 dùng TypeORM) 
-- migrations/002_add_categories_lessons.sql  (mỗi thay đổi 1 file, chạy theo thứ tự)
CREATE TABLE categories ( id SERIAL PRIMARY KEY, name TEXT NOT NULL, slug TEXT NOT NULL UNIQUE );

-- seed/01_categories.sql (dữ liệu mẫu, chạy sau migration)
INSERT INTO categories (name, slug) VALUES ('Backend', 'backend'), ('Database', 'database');
💡 Migration = "git cho schema"

Code bạn dùng git để version; schema database cũng cần version — không thì không ai biết bảng lessons được thêm khi nào, và không tái lập được môi trường giống nhau. Đây là mục lớn ở bài 23 (TypeORM migrations) — giờ bạn chỉ cần nhớ nguyên tắc: không bao giờ sửa schema bằng tay trên production, luôn qua migration.

9. Tổng kết — bạn vừa đạt được

  • Đọc được hạn chế của schema cơ bản bằng mắt senior (index, ON DELETE, mở rộng, versioning)
  • Hiểu và áp dụng chuẩn hóa 1NF/2NF/3NF (kể cả khi cố ý phá chuẩn)
  • Mở rộng schema: categories, lessons, instructor — users đóng 2 vai trò
  • Chọn đúng ON DELETE: RESTRICT / CASCADE / SET NULL theo nghiệp vụ
  • Tạo index cho khóa ngoại và chứng minh bằng EXPLAIN ANALYZE
  • Thống kê bằng LEFT JOIN + GROUP BY + HAVING (phân biệt WHERE/HAVING)
  • Áp dụng timestamps, soft delete, khóa thay thế đúng chỗ
  • Nắm nguyên tắc migration/seed — nền cho TypeORM ở bài 23

10. Câu hỏi tư duy (bắc cầu sang bài sau)

Tiếp theo là auth — hệ thống đăng ký thật cần xác thực người dùng trước khi đụng vào enrollments: ai được tạo khóa, ai mua khóa, mật khẩu hash sao cho an toàn. Bài 14 làm auth cơ bản bằng Express — bcrypt hash mật khẩu, JWT tạo token — và bắt lỗi email trùng (409) nhờ chính UNIQUE mà bạn đã hiểu ở đây.
