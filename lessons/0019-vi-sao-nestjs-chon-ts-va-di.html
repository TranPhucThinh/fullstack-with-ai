Vì sao NestJS chọn TypeScript + Dependency Injection?

Bạn đã thấy decorators (bài 17) và build TS (bài 18). Giờ ghép lại: NestJS không chọn TS vì "mốt" — mà vì TS + decorators + DI (Dependency Injection) giải quyết một bài toán mà Express để ngỏ: ai chịu trách nhiệm tạo ra các đối tượng trong hệ thống của bạn?

⏱ ~45 phút · 🎯 Mục tiêu: giải thích được Dependency Injection và Inversion of Control bằng ngôn ngữ của mình, chỉ ra vấn đề chúng giải quyết trong chính code Express của bạn, và tự dựng một "container" DI mini chạy được.

🌉 Bắc cầu từ cái bạn đã biết

Nhìn lại src/server.ts của dự án (bài 15): mọi route dùng chung một biến pool khai báo ở đầu file. Muốn "thay" dependency cho route, bạn phải sửa import hoặc thêm tham số. Còn ở bài 17 bạn đã có decorator @Register để đăng ký một class vào globalThis.__registry — đó chính là một nửa của Dependency Injection container. Bài này hoàn thiện nửa còn lại.

1. Vấn đề: ai tạo ra các đối tượng trong hệ thống?

Trong code Express của bạn, những đối tượng như pool, jwt, bcrypt được tạo ra ở ngoài cùng: viết tại module, rồi mọi handler import và dùng trực tiếp. Khi hệ thống lớn lên (đổi database, mock khi test, bật/tắt tùy môi trường), bạn phải sửa chính code người dùng — nói đúng hơn là sửa khắp nơi.

Diễn đạt theo thuật ngữ: đối tượng A phụ thuộc (dependency) vào đối tượng B. Câu hỏi kiến trúc đơn giản mà khó trả lời là: ai chịu trách nhiệm tạo ra B và đưa nó cho A? Có 3 đáp án:

Cách tạo dependencyAi tạo?Hệ quả

Một container trung tâm "tiêm" B vào AContainerA chỉ khai báo cần gì → nhận tự động; A không biết B được tạo thế nào
💡 Cốt lõi — tách "ai tạo" ra khỏi đối tượng

Ý tưởng chính của Dependency Injection: A không tự tạo B. Thay vào đó, một bên thứ ba (thường gọi là DI container / IoC container) nhận trước các "công thức tạo" cho từng đối tượng; khi một đối tượng báo nó cần dependency nào, container sẽ tạo đối tượng đó và tiêm vào. Việc kiểm soát "ai tạo gì" bị đảo ngược (inversion of control — IoC).

2. Trên code thật — Express đang làm theo kiểu nào

Bài 15 xây các handler kiểu này — mỗi handler tự mượn một singleton đã có sẵn từ ngoài:

src/server.ts — phong cách Express hiện tại 
import { pool } from './db.js'   // pool là một object dùng chung toàn file

app.get('/api/me/courses', auth, async (req, res) => {
  // PHỤ THUỘC pool được liệc trực tiếp — muốn đổi/mock thì sửa tại đây + mọi nơi
  const { rows } = await pool.query(`...JOIN...`, [req.userId])
  res.json(rows)
})

Vấn đề tinh vi: mọi handler biết quá nhiều về nơi lấy dependency (biết file db.js, biết biến pool). Muốn đưa pool giả (mock) vào để test route, handler không cho bạn — nó import trực tiếp file thật, nên test phải mở database thật hoặc đánh bạc hardcode. Đây là lý do NestJS xây DI ngay từ nền tảng:

  1. Test được: đối tượng nhận dependency qua tham số constructor → test chỉ việc tạo đối tượng kèm một mock đơn giản.
  2. Đổi được theo môi trường: cùng một "tên đăng ký", lúc dev dùng A, lúc production đổi sang B mà code không thay đổi.
  3. Quản lý tập trung: mọi object ra đời từ một nơi → dễ thêm log, kiểm soát vòng đời (lazy, singleton...).

3. DI hoạt động thế nào — "container" là gì

Một DI container gọn chỉ có 2 việc:

  1. Register — "khi ai đó cần tên X, hãy tạo theo công thức này".
  2. Resolve — khi một đối tượng báo "tôi cần X", container chạy công thức đã đăng ký để tạo X (và nếu X lại cần Y, lặp tiếp).

Bạn đã có nửa đầu: decorator @Register bài 17 đã ghi class vào registry. Nửa sau chính là resolve — một nơi sinh ra đối tượng theo nhu cầu. Đây là lý do NestJS gắn bó với TS + decorators: decorator là cú pháp khai báo metadata gọn, và TS cung cấp reflect-metadata để lúc chạy container biết được constructor đòi kiểu nào mà không cần viết tay. (Cơ chế đó sẽ thành code thật ở bài 20–21; giờ chỉ chốt ý tưởng.) Còn vì sao trước hết NestJS thích TS hơn JS thuần — đoạn sau nói rõ.

💡 Vì sao TS làm được điều Express không làm được

Express không hề biết "kiểu" của handler — mọi thứ đều là function nhận (req, res). NestJS ngược lại: @Controller / @Get / @Injectable gắn metadata lên class, và container dựng cây dependency tự động theo type. Express để người dùng tự nối; NestJS đòi khai báo cấu trúc thì máy dựng phần còn lại. Với type đầy đủ như TS, container làm việc đó chính xác — không phải đoán.

4. Nhào thật: dựng DI container mini trong dự án

Tạo file src/di-demo.ts (cạnh ts17-decorators-demo.ts) — bạn sẽ thấy mọi khớp nối của NestJS chỉ là phiên bản to hơn của cái này. Đã verify chạy XANH với TypeScript 7.0.2 + strict mode đúng như tsconfig dự án.

src/di-demo.ts — DI container mini (mô phỏng lõi NestJS) 
// Demo Bài 19 — container DI mini
// Chạy: npx tsx src/di-demo.ts (phải in ra "Course 1: NestJS bán")

// Hợp đồng: controller chỉ biết interface, không biết ai cài nó
interface Database { getCourseById(id: number): string }
interface CourseService { showCourse(id: number): string }

class Container {
  // "công thức" tạo từng dependency; resolve param là container để có thể lồng nhiều cấp
  private factories = new Map<string, (c: Container) => unknown>()
  private singletons = new Map<string, unknown>()

  register<T>(token: string, factory: (c: Container) => T): this {
    this.factories.set(token, factory)
    return this // trả this để nối chuỗi register().register()
  }

  // resolve: trả một bản duy nhất (singleton) nếu đã tạo; nếu chưa, chạy factory rồi lưu lại
  // Người gọi KHÔNG biết object ở đâu, ai tạo — quyền tạo đã nằm trong container
  resolve<T>(token: string): T {
    if (this.singletons.has(token)) {
      return this.singletons.get(token) as T
    }
    const factory = this.factories.get(token)
    if (!factory) throw new Error(`Không có provider cho "${token}"`)
    const instance = factory(this)
    this.singletons.set(token, instance)
    return instance as T
  }
}

// ===== REGISTER: đăng ký "cách tạo", chưa dựng đối tượng nào ngay =====
const container = new Container()
container
  .register<Database>('database', () => ({
    getCourseById(id) { return `Course ${id}: NestJS bán` }
  }))
  .register<CourseService>('courseService', (c) => {
    // courseService KHÔNG tự new database; mà "xin" (resolve) từ container
    const db = c.resolve<Database>('database')
    return { showCourse(id) { return db.getCourseById(id) } }
  })

// ==== Ai dùng cũng chỉ cần 1 lời gọi: "cho tôi courseService" =====
const svc = container.resolve<CourseService>('courseService')
console.log(svc.showCourse(1)) // Course 1: NestJS bán
// Thử lỗi: resolve tên CHƯA đăng ký thì ném lỗi ngay
// console.log(container.resolve<unknown>('chưa đăng ký'))
🛑 Trước khi chạy — tự kiểm bạn hiểu

Che lại khối register rồi tự hỏi: trong factory của courseService, vì sao gọi resolve('database') mà không sợ thiếu công thức? (Trả lời: vì register('database', ...) đã được gọi phía trên, trước khi resolve — thứ tự đăng ký trước, dùng sau.)

🔍 Góc phỏng vấn — câu hay hỏi

"DI là gì, tại sao dùng?" — gọn 3 lớp: (1) Kỹ thuật: để đối tượng nhận dependency qua tham số thay vì tự tạo; (2) Lý do: test được, đổi được theo môi trường, quản lý tập trung; (3) Máy móc: container giữ công thức tạo, resolve theo tên/type; NestJS kết DI + decorators thành một nền tảng uniform cho mọi module. Nếu được hỏi thêm — nhấc "singleton scope" mặc định của NestJS.

5. Câu hỏi tư duy (bắc cầu sang Module 4)

Bạn vừa tự dựng container với API gọi bằng tên chuỗi ('database', 'courseService'). Nhưng NestJS gọi bằng class, dùng constructor constructor(private readonly svc: CourseService) — không cần khai báo tên chuỗi nào cả.
