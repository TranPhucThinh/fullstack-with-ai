Node.js là gì — event loop, non-blocking I/O

Hiểu trái tim của Node: vì sao một luồng đơn (single-thread) có thể xử lý hàng nghìn request, và cái giá phải trả là gì.

⏱ ~50 phút · 🎯 Mục tiêu: giải thích được event loop là gì, phân biệt blocking vs non-blocking, và viết code chứng minh được sự khác biệt.

🌉 Bắc cầu từ cái bạn đã biết

Bài 03 bạn viết server với req.on('data') — bạn gom body bằng cách lắng nghe sự kiện, không phải chờ đợi. Tại sao lại viết kiểu đó? Vì Node không block khi đọc dữ liệu — nó nói "có data thì gọi tôi" rồi đi làm việc khác. Đó chính là non-blocking I/O và event loop — trái tim của Node.js.

1. Node.js là gì — V8 + libuv

Theo Node.js giới thiệu, Node.js là một runtime JavaScript được xây trên V8 (engine của Chrome) và libuv (thư viện C xử lý I/O bất đồng bộ).

Hai thành phần quyết định mọi thứ:

Thành phầnVai tròVí dụ
V8Biên dịch và chạy JavaScript — nhanh vì JIT-compiledBiểu thức 1 + 1, gọi hàm, tạo object
libuvXử lý I/O bất đồng bộ — đọc file, network, timerfs.readFile, http.createServer, setTimeout
💡 Vì sao lại cần libuv?

JavaScript trong trình duyệt chỉ có event loop cơ bản (click, fetch). Còn Node cần đọc file, connect database, làm network — những thứ đó là system calls của OS. libuv là lớp trung gian: Node gọi libuv, libuv gọi OS, rồi báo "xong rồi" qua callback. Nếu không có libuv, Node không thể làm I/O — nó chỉ là V8 chạy đơn thuần.

2. Single-thread — vì sao một luồng lại "kỳ diệu"?

JavaScript trong Node chạy trên một luồng (single thread). Nghĩa là tại một thời điểm, chỉ có một dòng code JavaScript được thực thi. Không có hai biến đếm tăng đồng thời, không có race condition trong code của bạn.

Nhưng nếu chỉ một luồng, làm sao server xử lý được 1000 request cùng lúc? Câu trả lời: Node không xử lý 1000 request cùng lúc — nó "trả lời" chúng theo lượt, nhưng không bao giờ chờ đợi I/O.

demo/blocking-vs-nonblocking.mjs — tạo thư mục demo trước 
// 📁 Tạo thư mục mới: mkdir -p elearning-backend/demo
// File: demo/blocking-vs-nonblocking.mjs

import { readFileSync, readFile } from 'node:fs'
import { fileURLToPath } from 'node:url'
import path from 'node:path'

const __dirname = path.dirname(fileURLToPath(import.meta.url))
const filePath = path.join(__dirname, 'sample.txt')

// ===== BLOCKING — đọc xong mới làm việc khác =====
// readFileSync: CHẶN luồng chính, không làm gì được cho tới khi đọc xong
console.log('1. Bắt đầu đọc file (blocking)...')
const dataSync = readFileSync(filePath, 'utf-8')
console.log('2. Đọc xong:', dataSync.trim())
console.log('3. Dòng này chỉ chạy SAU khi đọc file xong')
// ⛔ Output: 1 → 2 → 3 (tuần tự, không thể xen vào)

console.log('---')

// ===== NON-BLOCKING — đọc file, nhưng KHÔNG chờ =====
console.log('4. Bắt đầu đọc file (non-blocking)...')
readFile(filePath, 'utf-8', (err, data) => {
  // Callback này chạy SAU KHI file đọc xong — nhưng không chặn
  console.log('6. Đọc xong (callback):', data.trim())
})
console.log('5. Dòng này chạy NGAY, không chờ đọc file!')
// ✅ Output: 4 → 5 → 6 (dòng 5 chạy ngay, dù file chưa đọc xong)

3. Event loop — vũ điệu của các phase

Event loop là một vòng lặp vô hạn mà Node chạy ngầm, liên tục kiểm tra: "có việc gì cần làm không?". Nó chia thành nhiều phase, mỗi phase xử lý một loại callback riêng.

Theo Node.js docs — Event Loop, event loop có 6 phase, nhưng 3 phase quan trọng nhất với bạn:

PhaseXử lýCode liên quan
1. timersCallback của setTimeout, setInterval đã đến hạnsetTimeout(() => ..., 1000)
2. pollI/O mới — đọc file, network, request đếnreq.on('data'), fs.readFile
3. checkCallback của setImmediatesetImmediate(() => ...)

Giữa các phase còn có microtask queue (xử lý Promise, process.nextTick) — ưu tiên cao hơn. Đây là lý do promise resolve trước setTimeout dù cùng thời gian.

demo/event-loop-order.mjs — xem thứ tự chạy 
// File: demo/event-loop-order.mjs
console.log('1. Code đồng bộ — chạy ngay ở phase hiện tại')

// setTimeout: callback đưa vào phase timers
setTimeout(() => console.log('2. setTimeout(0) — phase timers'), 0)

// setImmediate: callback đưa vào phase check
setImmediate(() => console.log('3. setImmediate — phase check'))

// Promise.then: microtask — chạy NGAY sau code đồng bộ, trước phase tiếp
Promise.resolve().then(() => console.log('4. Promise.then — microtask (ưu tiên hơn timer)'))

// process.nextTick: microtask — trong cùng một microtask queue, thứ tự chạy phụ thuộc vào version Node
process.nextTick(() => console.log('5. process.nextTick — microtask CAO NHẤT'))

console.log('6. Code đồng bộ — cũng chạy ngay')

// Kết quả mong đợi: 1 → 6 → 5 → 4 → 2 (hoặc 3) → 3 (hoặc 2)
// ⚠️ Thứ tự giữa setTimeout(0) và setImmediate có thể khác nhau tuỳ phase hiện tại

4. Non-blocking I/O — lợi ích và cái giá

Vì sao non-blocking I/O lại mạnh?

So sánh — blocking server (mỗi request chờ nhau) 
// Giả sử mỗi request mất 2s đọc database (I/O)
// BLOCKING: request 1 → chờ 2s → trả → request 2 → chờ 2s → trả
// 2 request mất 4s

// NON-BLOCKING (Node): request 1 → gửi truy vấn DB → request 2 → gửi truy vấn DB → DB1 xong → trả → DB2 xong → trả
// 2 request mất ~2s (xử lý song song ở tầng I/O)

"Song song" ở tầng I/O, không phải ở code JavaScript của bạn. libuv dùng thread pool (mặc định 4 threads) để làm I/O nặng (đọc file, DNS). Network I/O thì dùng epoll/kqueue (cơ chế của OS) — không cần thread pool. Đó là lý do Node nhẹ: một tiến trình, không cần một thread cho mỗi kết nối như Apache.

⚠️ Cái giá của single-thread — CPU-bound task

Non-blocking I/O giúp ích cho I/O (đọc file, network, database). Nhưng nếu bạn có tác vụ nặng CPU (ví dụ: tính toán phức tạp, JSON.stringify file 1GB, vòng lặp 10 tỷ lần) — nó block toàn bộ event loop. Mọi request khác phải chờ. Giải pháp: worker_threads hoặc chia nhỏ tác vụ.
