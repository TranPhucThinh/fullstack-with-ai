Hiểu vì sao Node có HAI cách import (require vs import), cái gì quyết định dùng cái nào, và npm quản lý code của bạn ra sao.

🌉 Bắc cầu từ cái bạn đã biết

Bài 04 bạn viết import { readFileSync, readFile } from 'node:fs' và import { createServer } from 'node:http'. Nhưng sao lại là import mà không phải require? Và vì sao đôi khi bạn thấy code dùng require('express')? Đó là vì Node có hai hệ thống module — đây chính là bài học hôm nay.

1. Hai hệ thống module — CJS và ESM

Trong Node.js có hai cách đóng gói và tái sử dụng code:

CommonJS (CJS)ES Modules (ESM)
Ra đời2009 — sinh ra cùng Node.js, trước khi JS có chuẩn module2015 — chuẩn ES6 của JavaScript, sau này Node mới hỗ trợ
Nạprequire('./file')import x from './file'
Xuấtmodule.exports = ...export const ...
Khi nào chạyĐồng bộ — nạp xong file mới chạy tiếpBất đồng bộ — hỗ trợ top-level await
Đối tượngCó sẵn __dirname, requireDùng import.meta.url, không có __dirname sẵn
💡 Vì sao lại có HAI hệ thống?

Khi Node.js ra đời (2009), JavaScript chưa có chuẩn module nào — nên Node tự nghĩ ra CommonJS. Mãi tới 2015, JavaScript mới có chuẩn chính thức là ES Modules (import/export). Nhiều năm sau Node mới hỗ trợ ESM. Kết quả: cả hai vẫn tồn tại song song vì có hàng chục nghìn thư viện cũ viết bằng CJS chưa chuyển. Node không thể "xoá" CJS được — phải chạy được cả hai để không phá vỡ mọi dự án cũ.

2. Cái gì quyết định dùng CJS hay ESM?

Theo Node.js docs — Modules: Enabling, Node quyết định thể loại module của một file theo đuôi file + khai báo "type" trong package.json:

Đuôi fileThể loại module
.mjsLuôn ESM — bất kể "type" là gì
.cjsLuôn CommonJS — bất kể "type" là gì
.jsDo "type" trong package.json quyết định: "type": "module" → ESM; không có hoặc "commonjs" → CJS
⚠️ Quy tắc vàng — vì sao bạn đang dùng import

Kho elearning-backend/package.json của bạn có dòng "type": "module". Nên mọi file .ts/.js trong project mặc định là ESM → bạn viết import, không phải require. Nếu bỏ dòng đó đi, file .ts sẽ bị hiểu là CJS và import sẽ gãy. Đây là nguồn gốc của rất nhiều lỗi Cannot use import statement outside a module mà dev mới gặp.

3. Thực hành — demo CJS vs ESM trên máy thật

Tạo 2 file demo trong thư mục elearning-backend/demo/ (đã có từ bài 04). Chú ý: file .mjs và .cjs ép buộc thể loại, không cần quan tâm "type".

demo/hello.mjs — ESM, chạy trực tiếp 
// File: demo/hello.mjs
// .mjs → LUÔN là ESM, dù "type" trong package.json là gì

export const greet = (name) => `Xin chào, ${name}!`

// Chỉ chạy khi file này được chạy TRỰC TIẾP, không chạy khi được import
if (import.meta.url === `file://${process.argv[1]}`) {
  console.log(greet('An'))
}
demo/greet.cjs + demo/use-cjs.cjs — CommonJS 
// File: demo/greet.cjs — .cjs → LUÔN là CommonJS
module.exports = { greet: (name) => `Chào cjs, ${name}!` }
demo/use-cjs.cjs — require thay vì import 
// File: demo/use-cjs.cjs
const { greet } = require('./greet.cjs') // CJS dùng require, không phải import
console.log(greet('Bình'))
Terminal — chạy cả hai demo 
# Từ thư mục elearning-backend/
cd demo
node hello.mjs        # → Xin chào, An!
node use-cjs.cjs     # → Chào cjs, Bình!
✅ Đã kiểm chứng

Demo trên đã chạy đúng output trong sandbox với Node v24. Với máy bạn (Node v20 LTS) kết quả không đổi — cú pháp module này ổn định từ lâu.

4. package.json & npm — "trái tim quản lý" dự án

Mở elearning-backend/package.json — đây là file cấu hình mà npm/Node dựa vào để biết dự án chạy thế nào:

TrườngÝ nghĩa
"type": "module"Mọi file .js/.ts mặc định là ESM (quyết định import vs require)
"scripts"Lệnh rút gọn — npm run dev chạy tsx watch
"dependencies"Gói CẦN ở production (vd tsx để chạy)
"devDependencies"Gói CHỈ cần khi phát triển (vd typescript, @types/node)

Theo npm docs — package.json, `dependencies` là code mà app chạy được cần (cài cả trên server production), còn `devDependencies` chỉ phục vụ lúc phát triển/đóng gói (typescript biên dịch, type definition) — không cần khi chạy runtime.

5. 🎯 Mẩu chạy được — tách dữ liệu khóa học ra module riêng

Giờ bạn áp dụng ngay: tách dữ liệu khóa học khỏi src/server.ts vào một module riêng. Đây chính là cách bạn bắt đầu tổ chức code — đừng nhét mọi thứ vào một file, đó là thói quen gây rối khi dự án lớn dần.

src/courses.ts — module mới chứa dữ liệu + logic khóa học 
// File: src/courses.ts
// Module chứa dữ liệu khóa học + hàm thao tác — tách khỏi server.ts

export interface Course {
  id: number
  title: string
  price: number
}

// Danh sách khóa học tạm — chưa có database, bài 12 sẽ thay bằng PostgreSQL
export const courses: Course[] = [
  { id: 1, title: 'NestJS cơ bản', price: 500000 },
  { id: 2, title: 'Design Pattern cho Backend', price: 800000 },
]

// Hàm tạo id mới — tránh trùng với id hiện có
export function createCourseId(): number {
  return courses.length > 0
    ? Math.max(...courses.map((c) => c.id)) + 1
    : 1
}
src/server.ts — import module vừa tạo (chỉ giữ phần server) 
import { createServer } from 'node:http'
import { courses, createCourseId } from './courses.js' // import module riêng — chú ý đuôi .js

const server = createServer((req, res) => {
  // ... phần còn lại GIỮ NGUYÊN như bài 03,
  // nhưng dùng courses / createCourseId từ module thay vì khai báo lại
})
💡 Vì sao import phải ghi đuôi .js?

Trong Node ESM, khi import một file local bạn phải ghi đúng tên file sau khi biên dịch — tức là ./courses.js dù source là courses.ts (tsx sẽ tự map .ts → .js). Quy ước này của Node yêu cầu đuôi đầy đủ, khác với bundler (Vite/webpack) cho phép bỏ đuôi. Đây là điểm rất hay nhầm khi chuyển từ bundler sang chạy Node thuần.

Terminal — chạy & kiểm tra server vẫn hoạt động nguyên vẹn

npx tsc --noEmit        # 1. TypeScript pass (exit 0) — build thành công

npm run dev            # 2. Mở terminal khác, bật server

# 3. Kiểm tra — phải trả kết quả như trước khi tách module
